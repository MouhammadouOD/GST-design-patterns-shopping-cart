# Reflection Report

I built the shopping cart twice: once as plain procedural code with a module-scoped `cart` array and a handful of functions touching it directly, then again using the Module Pattern, where the array lives inside a closure and only `addItem`, `removeItem`, `clearCart` and `viewCart` are exposed.

The main challenge in the refactor was not the logic itself — `addItem`, `removeItem` and the total calculation stayed basically identical. The real work was making sure every function that needed to touch the cart was defined *inside* the same closure, closing over the same `items` variable. I actually caught a mistake here while writing a mutation test: I temporarily made `addItem` declare its own local `items` array by accident, and the total silently stayed at 0 instead of throwing an error. That is the real risk with the Module Pattern — it fails quietly if you break the closure, not loudly.

Correction after re-checking this claim: in plain Node CommonJS, the procedural version's `cart` variable is *already* just as unreachable from outside as `items` is in the Module version — neither was ever exported, and the "is undefined from outside" test passes identically for both (`proceduralCart.cart === undefined` and `cartModule.items === undefined`). That specific test does not actually demonstrate an advantage of the Module Pattern over plain procedural code in this environment, because Node's own module system already gives every file private scope by default. The real difference the test suite demonstrates is the closure-sharing mechanic itself: every exposed function (`addItem`, `removeItem`, `clearCart`, `viewCart`) closes over the *same* `items` variable, proven by a second `require()` of the module still seeing changes made through the first reference. Where the Module Pattern (IIFE) genuinely earns its keep is in an environment *without* per-file module scope — classic browser `<script>` tags sharing one global scope — where wrapping code in an IIFE is what creates that privacy in the first place. In Node, using it is harmless but largely redundant with what CommonJS/ESM already provide.

I would reach for a pattern like this over plain procedural code as soon as a module's internal state needs a real guarantee — for example, one shared cart for a whole checkout flow, not five. For a small script, quick CLI tool, or anything no reused twice, procedural code is still fine and faster to write.
